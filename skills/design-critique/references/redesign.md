# Redesign an existing interface

Use this workflow when the user wants to explore how an existing interface could look or feel. Start from the product, audience, core task, and the highest-impact findings in the skill's review. Use the existing design brief or `DESIGN.md` as the baseline when available.

Use the shared [design rules](../../frontend-design/references/design-rules.md), [domain and audience playbook](../../frontend-design/references/domain-audience-playbook.md), and [design system template](../../frontend-design/references/design-md-template.md) when available. Read the [image asset guidance](../../frontend-design/references/image-assets.md) when a direction needs generated imagery.

## Learn the user's taste

Ask up to four questions in one round if the answers affect the design. Cover what to keep, what to change, the desired feel, and any examples or fixed brand and platform constraints. Resolve an important audience or domain uncertainty within that round. When the user has already supplied direction, use it. If the user is unavailable, proceed with reasonable assumptions and state them.

When references are provided, name the traits that matter, such as type, density, imagery, color, or shape. Develop original designs from those traits. Keep platform conventions and the audience's needs as constraints.

## Explore directions

For an open exploration, show six to eight small previews of the same screen with the same content. Include one or two directions close to the user's references, a direction typical of the domain, a bolder option clearly labeled, and a spread of other styles. Use fewer directions when the request is narrower.

Use a short name for each direction and describe its character and how it serves the audience. Keep task clarity, accessibility, and essential controls across the options. Ask which two or three are closest and what the user wants to keep. If the user requests more options, reuse the brief and explore styles they have yet to see.

## Develop and refine

Summarize the brief before developing selected directions. Include the product and audience, what to keep and fix, the user's taste, selected or rejected references, and relevant typography, color, spacing, component, and icon decisions.

Create two or three higher-fidelity directions when the user wants a comparison. Use realistic domain content and a design canvas, a standalone mockup, or the user's requested format. Describe the trade-offs in each direction. Review the results against the same criteria as the original screen and fix the issues that would interfere with the task before presenting them.

Refine the chosen direction from feedback. If feedback is broad, show two or three variations of the element most likely to explain it. If several rounds stall, return to style exploration with the latest brief.

## Hand off the chosen design

Deliver the final design and related screens in the same style when requested. When establishing the design system, capture the approved choices in `DESIGN.md`, including tokens, component rules, relevant domain rules, and the rationale for decisions. If an existing `DESIGN.md` needs replacement, show the proposed differences and confirm before replacing it.

Provide a short, reusable handoff prompt that includes the target audience, platform, layout, constraints, and the applicable design system when the user needs to carry the design into implementation. Production implementation follows `frontend-design`.
